## 题一：CME 到底在删哪个位置时抛？

**文件**：`CmeLastFirst.java`（n=1..5 全枚举）

| 原表 | 删的位置 | 结果 |
|---|---|---|
| n=5 | 第 5 个（最后一个） | **抛 CME** |
| n=5 | 第 4 个（倒数第二） | 不抛 |
| n=5 | 第 1 个 | 抛 CME |
| n=2 | 第 1 个（此时也是倒数第二） | 不抛 |

**规律**：不抛 ⟺ 删完后 `cursor == size` ⟺ 删的是**原表的倒数第二个**。

`hasNext()` 的实现是 `cursor != size`，删最后一个后 `cursor(5) > size(4)` 仍然为 true → 循环继续 → 再调 `next()` → 对账失败。

> 这条推翻了"删最后一个不抛"的流行说法，day19 的题四又独立验证了一遍。

## 题二：手写 arraycopy 搬移 vs ArrayList.remove(0)

**文件**：`RemoveBench.java`（表大小 1000，remove(0) 执行 10 万次）

```
手写 System.arraycopy : 4.6 ms（46.1 ns/次）
ArrayList.remove(0)   : 4.2 ms（41.9 ns/次）
比值：1.10
```

**结论**：同一个量级。性能成本在 **O(n) 搬移**本身，不在"谁写的"。`remove(0)` 要搬 999 个元素，一次约 40ns 只说明 JIT + 内存带宽已经很猛。

## 题三：`set` 改不改 modCount？

**文件**：`SetVsAdd.java`（反射读 `AbstractList.modCount`）

```
遍历中 set(0, 99)  → 不抛
遍历中 add(99)     → 抛 CME

modCount 轨迹：创建 0 → set 两次仍 0 → add 后 1 → remove 后 2
```

**结论**：`modCount` 只统计**结构修改**（长度变化），`set` 是"内容修改"，不算。

坑：`modCount` 定义在 `AbstractList` 而不是 `ArrayList`，反射取字段要 `--add-opens java.base/java.util=ALL-UNNAMED`。

## 题四：1 万元素删 5 千，三种写法

**文件**：`RemoveAllBench.java`

```
removeAll(List)      :  20.93 ms
removeAll(HashSet)   :   0.15 ms   （139 倍）
removeIf + HashSet   :   0.37 ms   （57 倍）
```

**结论**：加速来自 **contains 从 O(m) 降到 O(1)**，不是 `removeAll` 换成 `removeIf`。

有意思的是 `removeIf + HashSet` 比 `removeAll(HashSet)` 慢 2.4 倍——`removeAll` 内部有批量压缩优化（BitSet 思路），`removeIf` 是逐个删。

**实战建议**：删少量用 `iterator.remove()`；删大量且能放进 Set 用 `list.removeAll(new HashSet<>(toRemove))`。

## 一句话总结

> **modCount 只管"长度变没变"；CME 的触发点是 `next()`；批量删除的真正杠杆是 `contains` 的复杂度，不是 API 的选择。**
